## Technical Findings

- **[CRITICAL]** `JC/backend/app/services/customer_bill_process.py:181,711,1136` — the customer-facing **bill/invoice** stores the *vendor's own internal product code* (`prod.vendor_product_id`) as the printed line "name"/description for every bill (`process_customer_bill`, `process_offline_customer_order`, `edit_customer_bill`). This flows straight into `compute_bill_totals()`'s `lines[].name` → `totals_json` → `_bill_items_table()`'s "Description" column in `JC/backend/app/services/doc_gen.py:150` (`desc = _cell(_safe(ln.get("name") or ...))`), i.e. it prints on the tax invoice the dealer receives/downloads/gets on WhatsApp. Contrast with `JC/backend/app/services/doc_gen.py:68-69`, which explicitly hard-codes `"name": ln.our_product_id` for the *order* document with the comment **"Customer-facing doc — never show the vendor's internal product code."** The same rule was clearly intended for bills but never applied there — a real information leak that lets a wholesale customer identify and go directly to the source vendor, undermining the trading margin/relationship. Fix: use `our_product_id` (or a proper display name field) for the bill line "name", the same way the order PDF already does.

- **[HIGH]** `JC/backend/app/routers/customer_orders.py:305-323` — the `bucket=billed` branch of `list_customer_orders` unconditionally applies the `day_start/day_end` filter (`CustomerBill.created_at >= day_start`) when the frontend is in "Today" mode. But "Billed" is an **actionable backlog** exactly like "New"/"Confirmed" — per `JC/web/admin/js/customer-orders.js:64-70` its own hint text says *"Bill sent — dispatch or collect payment first, then close."* Since the Customer Orders hub defaults to Today mode (`hubMode = "queue"`, `js/customer-orders.js:6-77`), a bill created yesterday that hasn't been dispatched/collected/closed yet **silently disappears from the default view** the next day — the exact "day-scoping hides actionable items" bug class already found and fixed for `received`/`open` (see the guard comments at `customer_orders.py:246-250` and `293-296`), but it was not applied to `billed`. Compare with the freight-parcel dispatch list (`JC/backend/app/services/freight_parcels.py:244`, `if day == "today" and status != "pending":`) which *does* correctly exempt pending/actionable rows from day-scoping — the same exemption is missing here.

- **[HIGH]** `JC/backend/app/services/bill_series_alloc.py:59-67` + `JC/backend/app/routers/customer_orders.py:1065-1103` (`patch_bill_number`) — manually renaming a bill number only checks for a clash against *currently non-cancelled* bills; it does not reserve/advance the owning series' `current_num`. If staff rename a bill to a number the series hasn't reached yet (e.g. series is at #100, staff types "#105" to correct a mistake), the series will later try to naturally allocate "#105" and hit `_assert_bill_number_free` → `HTTPException(400, "bill number ... already used on another open bill")`. This hard-blocks *all* billing on that series (not just that customer) until someone notices and manually skips the series pointer — with no UI affordance to do so. Also note `jc_customer_bills.bill_number` (`JC/backend/app/models/customer_bill.py:21`) has **no DB-level unique constraint** — uniqueness is enforced purely by an app-level check-then-write (`_assert_bill_number_free` then `row.current_num = next_num`); nothing in the database itself prevents a duplicate if any code path (or future bug) skips that check.

- **[MEDIUM]** `JC/backend/app/services/credit_limit.py:46-56` — `assert_credit_allows_bill()` is a no-op: *"Always allows billing — credit limits are informational warnings only, never blockers."* The `force_credit_override` parameter is threaded through `ProcessBillIn`/`EditBillIn` schemas, the router, `process_customer_bill`, `edit_customer_bill`, and the frontend (`JC/web/admin/js/customer-orders.js:40,1296,1898`) — but has **zero effect** on the outcome either way, and the frontend never even sets it to `true` (no UI control calls `CustomerOrders.setForceCredit(...)` with a real toggle — see Functional/Wiring). This is either dead code that should be removed, or a real, silent gap in credit-limit enforcement that the UI's "⚠ Over limit — Bill anyway" banner (`js/customer-orders.js:1364`) makes look like a deliberate soft-block when it never was one.

- **[MEDIUM]** `JC/backend/app/services/customer_returns.py:105-160` (`create_customer_return`) — `credit_amount` is a free-form staff-entered number, independent of the system-computed `calculated_amount`. The only validation is `credit_amount >= 0`; there is no upper bound, no required extra confirmation/permission when `credit_amount` deviates materially from `calculated_amount`, and no audit flag on the return itself for "manually adjusted amount." A fat-finger or bad-faith entry (e.g. crediting ₹50,000 against a ₹500 return) posts straight to the AR ledger as a `credit_note` with no guardrail.

- **[MEDIUM]** `JC/backend/app/routers/shop.py:622-687` (`list_order_history`, `list_my_orders`) — N+1 queries on the dealer's own order-history page: for every order line, `db.get(CatalogProduct, ln.catalog_product_id)` is called individually, and for every *shipped* line `_find_bill_for_line()` (`shop.py:523-536`) runs its own `CustomerBill` join+filter+order_by query. A dealer with dozens of past orders triggers dozens of extra round-trips on a page they're likely to open often.

- **[MEDIUM]** `JC/backend/app/routers/shop.py:523-536` (`_find_bill_for_line`) — the bill shown against a shipped portal order line is guessed heuristically ("most recent bill for this customer+product created at/after the order's `placed_at`"), not tracked via a real foreign key. If a dealer has two orders for the same product and multiple bills are raised afterward, a line can be attributed to the **wrong bill number** in the portal's order history — a customer-visible correctness bug, not just cosmetic.

- **[LOW]** `JC/backend/app/routers/shop.py:673` and `:747` — `has_bill_document=bool(bill and (bill.document_key or True))` and `has_bill_document=bool(bill and bill.document_key) or bool(bill)`. In both cases the `or True` / `or bool(bill)` neuters the `document_key` check entirely — the field always just equals "a bill was found," regardless of whether a PDF actually exists yet. Harmless today only because the document is lazily generated on download, but the code reads as broken and will mislead the next person who touches it.

- **[LOW]** `JC/backend/app/routers/customer_orders.py:14-20` (`_local_day_bounds_utc`) — reimplements IST-day-boundary math locally instead of importing `ist_day_bounds_utc` from `app/services/biz_date.py` as the project convention requires (see workspace rule on `biz_date.py`). Functionally equivalent today, but it's a second copy of date-math that can silently drift from the canonical helper.

- **[LOW]** `JC/backend/app/services/ledger.py:288-291,338-342` (`build_customer_ledger`) — `LedgerLineDetail.buying_price` is populated with `format(ln.unit_price, "f")` (the *selling* price), not a real cost figure — confusing because the exact same `LedgerLineDetail` schema is used for the vendor ledger (`ledger.py:66`) where `buying_price` **is** the real, `hide_cost()`-masked buying price. No cost is actually leaked today (the value stored is selling price either way), but this is a booby trap: a future edit that "fixes" this by wiring in the real `CatalogProduct.buying_price` would leak true cost to any staff with only `customers.read`, since this endpoint never calls `cost_visibility.hide_cost()`.

- **[LOW]** `JC/backend/app/services/customer_returns.py:210-213` — `generate_customer_return_document()` is called synchronously inside `create_customer_return()` (wrapped in bare `except Exception: pass`). Every other customer-facing document flow (order placement, offline order, bill submit) explicitly **defers** PDF generation to the first download specifically because "sync S3/PDF was hanging the Save button for 30–90s" (see comments at `customer_orders.py:1274` and `submit_process_bill`). Returns reintroduce that exact hang risk on the "Submit return" action.

- **[INFO]** `JC/backend/app/services/void_service.py:388-396` (`void_customer_placement`) — only reverses stock/cancels when `placement.status == "received"`; voiding a placement whose status is `"open"` or `"billed"` (post-confirm history rows) silently no-ops on the stock/qty side and just hides the row. This is safe under the current data model (the real running balances live on `CustomerOpenLine`/`CustomerBill`, not the placement), but it's easy for a future change to assume "void = full reversal" and introduce a real stock leak here.

## Functional / Wiring Findings

- **[MEDIUM]** No UI control ever sets `force_credit_override` to `true`. It's declared (`js/customer-orders.js:40`), sent on every bill submit/edit (`:1296`), and has a setter (`setForceCredit`, `:1898`, exported at `:2732`) — but no `onclick`/`onchange` anywhere in `customer-orders.js` calls `CustomerOrders.setForceCredit(...)`. Combined with the backend no-op above, this is dead plumbing end-to-end: the affordance a PM would expect ("tick a box to confirm you're overriding the credit limit") does not exist in the UI, and wouldn't matter server-side even if it did.
- **[LOW]** `PATCH /customer-orders/bills/{id}/number` UI (`promptEditBillNumber`/`saveBillNumber`, `js/customer-orders.js:1568-1596`) tells staff only "Must be unique among open bills" — it gives no warning about the future-series-collision risk described in the Technical section, so staff have no way to know they might be about to jam the series.
- **[LOW]** `sendCredentials()` (Send login → `POST /customers/{id}/reset-password`) and `resendWhatsApp()` (`POST /customers/{id}/resend-whatsapp`) do functionally the same thing (mint a new password, send via WhatsApp) but are wired to two differently-labeled, differently-reachable UI entry points ("Send login" on the profile footer vs. "Retry WhatsApp" only inside the create-wizard success screen). Not broken, but confusing — a staff member who wants to resend a forgotten password from the customer's *profile* (not right after creating them) only ever sees "Send login," which silently invalidates the old password too; there's no lower-friction "just resend the same WhatsApp" option.

## PM / UX Suggestions

- **[CRITICAL]** The printed customer invoice shows the vendor's own product code (see Technical §1). Beyond being a bug, from a business standpoint this is actively helping wholesale customers disintermediate the business — recommend an urgent audit of any other outward-facing document for the same leak (order PDF was already fixed; return PDF and bill PDF should be spot-checked again after the fix).
- **[HIGH]** The "Bill anyway" credit-limit banner (`js/customer-orders.js:1364`) reads like a deliberate soft-block/override step, but nothing is actually blocked or overridden — recommend either (a) making the language honestly informational ("Outstanding will exceed credit limit — this is a heads-up only, billing is not blocked"), or (b) actually implementing a hard/soft stop with a real override control if the business wants credit limits to mean something. Silently-cosmetic limits on a wedding-card wholesale book (where a handful of large unpaid dealers can materially hurt cash flow) is a real business risk, not just a UX nit.
- **[HIGH]** "Billed" tab defaults to Today-only (see Technical §2) — a bill from a prior day that's awaiting dispatch/payment/closing simply vanishes from the default view. For a small staff team relying on the daily queue to know what's outstanding, this is exactly the kind of bug that causes a real dispatch/collection to get forgotten, mirroring the previously-fixed New/Confirmed bug.
- **[MEDIUM]** Return credit amount: the wizard shows "Edited amount becomes final AR credit, even if different from calculated" (`js/returns.js:404`) with no confirmation step when the two diverge. Recommend a visible warning/second confirmation ("You entered ₹X but the calculated value is ₹Y — confirm?") before submit whenever the two differ by more than a rounding tolerance, to catch fat-finger entry before it posts to AR.
- **[MEDIUM]** Customer creation wizard (`app.js` step 1) buries GST number, address, and additional details behind a collapsed "More" `<details>` — fine for speed, but there's no field for `party_number` (staff cannot assign/see the auto-number until after creation) even though the backend supports a custom one; if the business tracks physical ledger/party numbers that predate the system, staff currently cannot align them at creation time and would need a follow-up edit (which the edit form also doesn't expose — `party_number` isn't editable anywhere in the UI).
- **[MEDIUM]** "Cash" vs "Credit" customer toggle in both the create wizard and edit form force `credit_limit` to blank/0 with no explanation of what happens to an *existing* customer's outstanding balance if they're switched from Credit to Cash — worth a one-line inline note ("Switching to Cash does not clear existing dues — see AR").
- **[LOW]** Delete customer confirmation ("Move customer to recycle bin? They cannot login until restored.") is good, but "Mark Inactive" and "Restore to Active" use a generic `confirm()` browser dialog with no context about what Inactive actually changes (can they still be billed? Still show in AR lists?) — a short one-liner in the confirm text would reduce support questions from newer staff.
- **[LOW]** The "Send login" button always mints a brand-new password and invalidates the old one (per backend comment "cannot resend old plain password") but the button label doesn't say this — a staff member who just wants to remind a dealer of their existing password (e.g. dealer says "I forgot, can you resend?") will unknowingly issue a new one every time they click it. Consider renaming to "Reset & resend password" to set the right expectation.
- **[LOW]** Bill-number correction dialog ("Temporary correction. Must be unique among open bills.") doesn't explain *why* someone would need this, which invites uncontrolled use — since it can jam a series (see Technical), recommend gating this action to admin-only with a stronger warning, or removing it in favor of a supported "skip/reserve a series number" tool.
