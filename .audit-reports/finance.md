# JC ERP — Finance & Reporting Module Audit

Scope: `JC/backend/app/{models,routers,services}` (expenses, AP/AR ledgers,
finance overview, dashboard, reports_extended/reports) and
`JC/web/admin/js/{finance,dashboard,addon-products,payment-modes}.js`.
`backend/` (repo root, no `JC/` prefix) is the unrelated app and was not
touched.

---

## Technical Findings

- **[critical]** `JC/backend/app/routers/debit_notes.py:67-91` (`list_debit_notes`, `get_debit_note`) — these two GET endpoints only depend on `get_auth_context` (i.e. "any authenticated staff, any permission set"), with **no** `require_permission(...)` at all. `DebitNoteOut` (`app/schemas/debit_note.py`) returns `amount`, `payable_effect` (a real AP money figure), and `vendor_label` unmasked — only `unit_price` goes through `hide_cost()`. Every other mutation on this router (`create`, `update`, `void`) correctly requires `vendor_orders.write`; the read endpoints were evidently missed. Result: a staff member with e.g. only `setup.read`/`catalog.read` (zero vendor/AP visibility) can call `GET /debit-notes` and see every vendor's debit-note amounts and AP impact.

- **[critical]** `JC/backend/app/routers/addons.py:196-232` (`receive_addon_stock`) — gated only by `addons.write`. When `body.total_cost` is set it directly creates an `Expense` row (`category="addon stock"`) that flows straight into `finance_overview()`'s `expense_total`/`cost_mix`/`cash_pulse.cash_out` and into `/reports/pnl` and `/reports/expense-by-category`. `addons.write` is granted by the "Buy" and "Stock" role presets in `JC/web/admin/js/staff.js:104-122`, neither of which includes `finance.write` — so a warehouse/purchasing-only staffer with **zero** finance permission can inject arbitrary book expenses (schema only enforces `total_cost >= 0`, no upper bound). This bypasses the entire `finance.write` gate that `app/routers/expenses.py:70-96` (`create_expense`) otherwise enforces for expense creation. It's also the only Expense-creation path in the codebase that isn't wrapped in `log_from_auth(..., entity_type="expense", ...)` — only the addon stock-quantity update is activity-logged, so the money movement itself has no audit trail entry.

- **[high]** `JC/backend/app/routers/freight_agents.py:124-129` (`list_freight_agents`) — gated by `require_any_permission("vendor_orders.read", "customer_orders.read")`. Both permissions are part of the base "Accountant" preset (`ACCOUNTANT_PERMS` in `JC/backend/scripts/create_accountant_staff.py:30-39`), which per the business rule should have **no** finance visibility (no AP/AR/P&L) unless separately granted. This endpoint returns each agent's `balance_due`/`outstanding` (an AP-like finance figure) to any staffer holding either read permission — i.e. Fiza/Raj (who were deliberately *not* given `ar.read`/`ap.read`) can see real outstanding money owed to freight agents.

- **[medium]** `JC/backend/app/services/dashboard.py:83-133` (`build_dashboard`, AR/AP "dues" sections) — hand-rolls the exact same join+`SUM(e.amount)`/`HAVING > 0` SQL that `ar_dues_total()`/`ap_dues_total()` (`app/services/ar_ledger.py:425-457`, `app/services/ap_ledger.py:708-739`) already implement, instead of calling those functions or `dues_snapshot()`. This is precisely the anti-pattern `app/services/money.py:44-47` warns against ("never re-sum raw ledger types in the UI or ad-hoc overview formulas"). The two copies are numerically identical today, but nothing enforces that — a future change to the canonical AP/AR dues definition (new entry type, extra filter, freight netting, etc.) will silently desync the Home dashboard's `top_collect`/`top_pay` from the Finance hub's `/finance/dues`, exactly the class of bug `assert_dues_consistent()` was built to catch, yet this code path is outside that check.

- **[medium]** `JC/backend/app/models/expense.py` + `JC/backend/app/routers/expenses.py:99-115` (`delete_expense`) — `Expense` is hard-delete-only and the delete endpoint only blocks deletion when `row.freight_agent_id` is set (freight settlements are protected because `FreightLedgerEntry.expense_id` links back to them, see `app/services/freight_ledger.py:89-103`). The `"addon stock"` expenses created by `addons.py` (finding above) have **no** equivalent link/protection — there's no `addon_product_id`/`addon_stock_ledger_id` column on `Expense`, so an admin can freely hard-delete one with zero warning, silently erasing that stock-cost from every P&L/expense aggregate while the corresponding `AddonStockLedger` "received" row and current on-hand quantity remain untouched, with only loose text (`category`/`reference`/`description`) to ever reconstruct the connection.

- **[low]** `JC/backend/app/services/finance_overview.py:64-67,220-233` — `/finance/overview`'s `revenue` field is actually **cash collected from customers** (`mag(ar_payment_sum)`, netted against reversals), and `profit`/`profit_is_net_cash` is net cash, not accrual profit. Meanwhile `/reports/pnl` (`reports_extended.pnl_detail`) uses `revenue`/`net_sales`/`net_profit` to mean actual bill-based accrual figures. The two endpoints reuse the same English words for different money models. The admin frontend correctly relabels this today (`finance.js` `CHART_LABELS`: `revenue → "Cash in"`, `profit → "Net cash"`), which is why it isn't a live user-facing bug — but the raw API contract is a footgun for any future consumer (mobile app, export, another dev) that doesn't know to relabel.

- **[low]** `JC/backend/app/services/finance_overview.py:161-188` — the `ap_vendors`/`ar_customers` top-10 arrays returned by `/finance/overview` hardcode `opening_total`, `bill_total`, `debit_note_total`/`credit_total`, `payment_total` to `"0.00"` and `transaction_count` to `0` for every row (only `outstanding`/`*_label` are real). Confirmed dead: the only frontend consumer (`finance.js:1777`, `hBarList`) reads just `customer_label`/`outstanding`. Harmless today, but it's fake data sitting in a public API response — a bug waiting for the next developer who trusts a field that looks real.

- **[low]** `JC/backend/app/routers/payment_modes.py:44-50` (`list_payment_modes`) is gated by `finance.write` alone, while the settle flows that consume it (`settle_vendor_ap`/`settle_customer_ar` in `accounts_payable.py`/`accounts_receivable.py`) are gated by `ap.write`/`ar.write`. Every *current* accountant (Nikhil/Fiza/Raj) happens to hold `finance.write` too, so this hasn't surfaced yet, but any admin who grants a custom staff role `ar.write`/`ap.write` without also ticking `finance.write` (fully possible via the free-form checkbox UI in `staff.js`) will find the payment-mode picker 403s and the Settle button becomes unusable for that role.

## Functional/Wiring Findings

- **[high]** `JC/backend/app/routers/dashboard.py:24-44` (`get_dashboard`) — for every non-admin, `data["pulse"]`, `data["top_collect"]`, `data["top_pay"]` are unconditionally cleared, and the `allowed` action-card set only ever checks `customer_orders`/`vendor_orders`/`returns`/`low_stock` permissions — `ar.read`/`ap.read` are never consulted, so the `"collect"`, `"pay_vendors"`, `"freight"` action cards can never appear for a staff account no matter what they're granted. Concretely: `grant_nikhil_ar_ap.py` was written specifically to give Nikhil "full AR/AP access (outstanding figures, ledger, payment collection/payment with real context)" — but the Home dashboard still shows him nothing about AR/AP; he only sees any of it once inside the Finance hub itself (`finance.js:195`, which *does* correctly check `ar.read`/`ap.read`). The hub is wired right; the dashboard summary is not.

- Cross-checked every AP/AR/expense/freight button → endpoint pair (`settle`, `record-payment`, `reverse`, `void`, `opening-balance`, `upload-payment-receipt` in `finance.js` against `accounts_payable.py`/`accounts_receivable.py`/`freight_agents.py`) and confirmed the permission scope required server-side matches the permission the frontend checks before showing the button (`ctx.can?.("ar.read")`/`ctx.can?.("ap.read")` at `finance.js:141,153,195-196,801,1150,1157,1226`). No mismatches found here — this part of the defense-in-depth (frontend hide + backend enforce) is done correctly.

- **[medium]** `JC/web/admin/js/finance.js:280-378` (`quickVendorPayment`/`quickCustomerPayment`/`quickAddExpense`, the accountant "quick entry" flow) chains several native `prompt()`/`confirm()` dialogs with **no final review screen** showing the assembled entry (party, amount, mode, ref) before it POSTs. Because this role by design cannot view AP/AR totals, ledgers, or the expense list afterward (`GET /expenses` and `GET /accounts-payable|receivable` are gated above `finance.write`), a mistyped amount (`5000` vs `50000`) is committed silently and is only discoverable by the admin reconciling later — there is no path for the accountant themselves to catch or flag it.

- **[low]** `JC/web/admin/js/addon-products.js:212-219` — the `total_cost` prompt for "receive stock" has no unit label, no numeric formatting, and (per the Technical finding on `addons.py`) is the *only* gate standing between an `addons.write`-only staffer and a real book expense; there's no confirmation step here either.

## PM/UX Suggestions

- **[high]** Clarify "Cash in"/"Net cash" vs true revenue/profit. The Finance hub's cash-pulse card already relabels `revenue`→"Cash in" and `profit`→"Net cash" in the UI, which is good, but the explanatory note ("Cash movement only — not books P&L…") is a small caption most staff will skim past. Recommend a persistent, slightly more visible badge/tooltip on the cash-pulse card itself (not just a footnote) so a non-accountant glancing at the Home/Finance screen doesn't conflate "money that came in today" with "how much we made." Rationale: the backend already keeps these concepts cleanly separate (`cash_pulse` vs `books_snapshot` vs `/reports/pnl`); the risk is purely in how prominently the distinction is surfaced.

- **[medium]** Give the "Quick entry" (accountant) role a lightweight feedback loop: a "Your entries today" list (date, party, amount, mode — no running totals/outstanding) so Fiza/Raj/Nikhil can visually confirm what was actually recorded, without exposing anything the restricted role is meant to hide. Today the only feedback is a transient toast; if it's missed or a value was mistyped, there is no self-service way to notice. Rationale: reduces reliance on the admin to catch data-entry mistakes after the fact, without loosening the visibility restriction itself.

- **[medium]** Extend the Home dashboard for AR/AP-scoped staff (see Functional finding above) so a grant like Nikhil's actually shows up where an admin would expect it — even a minimal "Collect ₹X from N customers" / "Pay ₹Y to N vendors" card, mirroring what admins see, would close the gap between "what permission was granted" and "what the user actually experiences."

- **[low]** Payment-mode visual distinction: cash vs bank currently renders as plain text (`payment_mode` string) inline in the ledger rows. A small icon or colored chip (e.g. 💵 vs 🏦) next to each AR/AP ledger row would make it much faster to eyeball a day's collections and separate cash-in-hand (needs physical deposit/tallying) from bank transfers (already settled) — this is the kind of distinction accountants scan for constantly.

- **[low]** The expense category filter in `finance.js` (`renderExpenseFilters`) is a hardcoded list (`rent, salary, electricity, transport, misc, other`) that doesn't include `"addon stock"` (or any future ad-hoc category), even though the backend accepts and aggregates arbitrary categories (`/reports/expense-by-category` already computes the real set). Recommend deriving the filter dropdown from that endpoint instead of a static list, so new categories are filterable as soon as they appear rather than only visible in the unfiltered "All" view.
