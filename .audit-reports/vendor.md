# Vendor & Vendor Billing Module — Audit Report

Scope: `JC/backend/` (vendors, vendor orders, receipts/bills, debit notes, AP ledger, void/recycle) and `JC/web/admin/js/{vendors,vendor-orders,stock,debit-notes}.js`. Baseline: `cd JC/backend && python3 -m pytest tests/ -q` → **117 passed** (verified before writing this report; day-scoping bugs for "placed"/"received" queues are already fixed and covered by tests — see `test_ops_fix_pack.py`).

---

## Technical Findings

- **[high]** `JC/backend/app/services/stock_receipt.py:25-40` (`get_or_create_open_order`) — race condition: it catches `IntegrityError` to handle a concurrent-insert collision, but `JC/backend/app/models/vendor_order.py:17-18` only declares a non-unique `Index` on `(vendor_id, bucket, is_open)`, not a `UniqueConstraint`. Two concurrent requests (e.g. two staff placing an order for the same vendor at the same moment, or a double-tapped "Place order") can both pass `get_open_order()` returning `None` and both insert a new `VendorOrder` row — no `IntegrityError` is ever raised to trigger the fallback. Result: two "open" `placed` orders for the same vendor, which breaks the "one open order per vendor+bucket" invariant every other query (`_build_detail`, `_to_bill_summaries`, hub cards) assumes.
- **[high]** `JC/backend/app/services/vendor_receive_bill.py:175-183` (`bill_receipt`) and `receive_vendor_goods` (same file, ~line 45-100) — no `with_for_update()` (or any lock) on the `StockReceipt` row before checking `bill_status`/pending qty and then mutating it. Two near-simultaneous submits of the same bill (double-click, or a slow network response causing a user to click "Submit Bill" twice) both read `bill_status == "pending_bill"` before either commits, and both proceed to post a `post_bill_entry` — duplicating the AP bill amount for one receipt. This is compounded by **[B-1 below]**: the frontend never disables the submit button while the request is in flight.
- **[high]** `JC/backend/app/routers/debit_notes.py:112` — `void_debit_note_endpoint` is gated with `require_permission("vendor_orders.write")`, **not** `require_admin`. Every other void in this module (`JC/backend/app/routers/stock.py` receipt-void, and every restore/purge in `recycle_bin.py`) is admin-only. A staff member with plain `vendor_orders.write` (not admin) can void a debit note — reversing its AP and stock effects — with no admin gate. This is an inconsistency with the stated rule ("Void/purge/... admin-only regardless of staff permissions") and with the sibling receipt-void endpoint one file over.
- **[high]** `JC/backend/app/routers/debit_notes.py:68-91` — `GET /debit-notes` (`list_debit_notes`) and `GET /debit-notes/{id}` (`get_debit_note`) only depend on `get_auth_context` — i.e. **any** authenticated staff member, even one with zero granted permissions, can list every debit note for every vendor (amounts, notes, bill numbers). Every other read endpoint in this module (`stock.py`, `vendor_orders.py`, `accounts_payable.py`) requires a specific `*.read` permission. This is a real permission gap — a staff account scoped to, say, only `customers.read` can still pull the full vendor debit-note history.
- **[medium]** `JC/backend/app/services/vendor_receive_bill.py:211-227` (`bill_receipt`) and the matching block in `receipt_edit.py:_edit_bill` — the one-off `billing_pct_override` / `gst_rate_pct_override` (which change how much we actually owe the vendor for *this* bill) are only gated by `vendor_orders.write`. Changing the vendor's **permanent default** for the same two numbers (`PATCH /vendors/{id}/billing-terms`, `JC/backend/app/routers/vendors.py:170-192`) is explicitly admin-only. A non-admin staff member can't change the vendor's profile split-billing %, but can achieve the same net financial effect one bill at a time without any admin gate — an inconsistent trust boundary for a money-sensitive input.
- **[medium]** `JC/backend/app/routers/vendor_orders.py:1294-1334` (`update_open_line`, `PATCH /vendor-orders/open-lines/{id}`) — when the request changes `catalog_product_id`, the code sets `row.catalog_product_id = prod.id` with no check for an existing `VendorOpenLine` row for that `(vendor_id, catalog_product_id)` pair. `jc_vendor_open_lines` has `UniqueConstraint("vendor_id", "catalog_product_id")` (`JC/backend/app/models/vendor_open_line.py:18`) that applies regardless of status (open/closed/cancelled) — see the reuse pattern in `_get_or_create_open` (`open_lines.py:11-29`). If the vendor already has *any* row for the target product, this PATCH throws an unhandled `IntegrityError` on commit → generic unhandled-exception response (no FastAPI global exception handler is registered in `main.py`) → the staff member sees an opaque error instead of "this product already has a pending/closed line for this vendor."
- **[medium]** `JC/backend/app/routers/vendors.py:226-247` (`create_vendor`) — the `except IntegrityError` handler unconditionally reports `"phone already registered"`, but the insert can also fail on the `vendor_number` unique constraint: (a) the auto-generated `SELECT MAX(vendor_number)+1` (line ~230) is itself a race — two concurrent vendor creations without an explicit `vendor_number` can compute the same next number before either commits; (b) a staff member can also pass an explicit `vendor_number` that collides with an existing vendor. In both cases the user is told their **phone** is duplicated, which is simply wrong and will send staff hunting for a phone-number typo that doesn't exist.
- **[medium]** No uniqueness check anywhere (schema, DB, or app logic) on `bill_number` or `order_receipt_number` (`JC/backend/app/models/stock.py:49-50`, `VendorBillIn`/`VendorReceiveCreate` in `schemas/stock.py`). Nothing stops the same vendor paper-bill number from being entered twice for the same vendor (e.g. re-billing a receipt that was actually already billed under receipt-edit, or a copy-paste mistake across two different receipts), silently double-posting AP for one physical invoice. Given the "one bill per receipt" model (see PM finding below) this is a real, plausible data-entry failure mode, not just a theoretical one.
- **[medium]** Add-on vendor purchases never touch the vendor AP ledger. `AddonProduct` carries its own `vendor_id` (`JC/backend/app/models/addon_product.py:19`) and its own `quantity_on_hand` field, but `POST /addons/{id}/receive-stock` (`JC/backend/app/routers/addons.py:197-233`) only calls `add_addon_stock` + optionally logs a hard-deletable cash `Expense` — it never calls anything in `ap_ledger.py`. Since `StockReceiptLine.catalog_product_id` FKs only to `jc_catalog_products`, there is no `StockReceipt`/`DebitNote`/AP path for addon products at all. Per the stated business context ("add-on items... from separate vendors"), if any add-on vendor extends credit rather than being paid cash-on-delivery, **there is no way to track what's owed to them** — they never appear on that vendor's AP/"Pay" tab, ledger activity, or statements, even though they have a `vendor_id` that implies they should.
- **[medium]** `JC/backend/app/models/vendor_order.py:63` `VendorOrderLine.quantity_remaining` is a stale/dead-in-practice field for the "placed" bucket: it's initialized to `quantity` on placement create (`vendor_orders.py:1135`) and on cancel-copy (`:1212`, `:1526`), and is only otherwise touched by a direct line edit (`update_line`, `:1586` — `line.quantity_remaining = body.quantity`, i.e. just re-set to the new full quantity). It is **never decremented when goods are received or billed against that line** — real pending/received/billed tracking lives entirely in the separate `VendorOpenLine` table (`open_lines.py`) and `StockReceiptLine`. Yet `PlacementLineDetail.quantity_remaining` (`vendor_orders.py:332`) copies this stale column straight through to the API, and `services/ledger.py:64` also surfaces it. It happens to be dead in the current UI (see Functional finding on `renderReceivedExpand`), but it's a landmine: any future feature that trusts this column will show wrong numbers.
- **[low]** N+1 pattern in `JC/backend/app/routers/vendor_orders.py:229-259` (`_build_detail`) — for each placement in a vendor order it runs a separate `VendorOrderLine` query (line ~242) and, when `bucket in ("billed","received")`, a separate `StockReceipt` lookup (line ~250-258). A vendor with dozens of historical placements will fire dozens of extra queries every time its order detail is opened. Contrast with the already-batched `_vendor_contexts`/`_summaries_from_orders` helpers in the same file, which show the pattern the rest of the module correctly follows.
- **[low]** `JC/backend/app/routers/accounts_payable.py:172-187` (`record_vendor_payment`, "entry-only" role for `finance.write` staff) checks only that `outstanding > 0` before accepting a payment `amount` — there is no upper bound relative to `outstanding`. Combined with the fact that this role, by design, "never reveals outstanding/totals," an accountant-role staff member has literally no on-screen number to sanity-check their entry against and nothing stops a 10x fat-finger from posting (see PM finding for the UX angle).

## Functional / Wiring Findings

- **[high]** `JC/web/admin/js/stock.js` — the "Confirm receive" (line ~1118) and "Submit Bill" (line ~1276) buttons in the receive/bill wizard never disable themselves or guard against a second click while `submitReceipt()` (line 1643) is in flight, unlike `Vendors.create()` in `vendors.js:594` which does `btn.disabled = true`. Combined with the missing server-side lock (Technical finding above), a slow connection + impatient double-tap can duplicate a receive or a bill.
- **[medium]** `JC/web/admin/js/vendor-orders.js:344-345` — the "Open vendor" / "View vendor" link on the "To bill" open-hub card calls `VendorOrders.openDetail(o.id || 0, 'received', vendorId)`. Since the "received" `VendorOrder` bucket is dead in the one-receipt-per-bill model (`o.id` is always `0` from `_to_bill_summaries`, confirmed in the backend's own code comment at `vendor_orders.py:104-111`), `openDetail` (lines 800-829) falls through every branch and ends up with `currentOrder = null`. `renderDetail()` (line 970-977) then shows an empty state — **"No Received — Nothing for this vendor in this stage"** — for a vendor that the hub card just showed *has* receipts pending bill. This is a real "action succeeds but screen doesn't show the state" bug: the workaround (expand "Show lines" on the card itself) exists, but the dedicated detail page for this bucket is non-functional for any vendor.
- **[low]** `JC/web/admin/js/vendor-orders.js:462-483` (`renderReceivedExpand`) is dead code — defined but not called from anywhere in the file (confirmed via full-file search). It's the frontend twin of the dead backend `VendorOrder.bucket == "received"` path in `_build_detail`. Safe to delete; currently just a maintenance trap for a future developer who tries to "fix" it by wiring it up (it would surface the stale `quantity_remaining` data noted above as "Unbilled" qty).
- **[low]** `GET /vendors/{id}/billing-terms` (`JC/backend/app/routers/vendors.py:161-167`) is not called anywhere in `JC/web/admin/js/*` — the admin frontend only ever fetches billing terms nested inside `GET /vendors/{id}` and writes them via the separate `PATCH .../billing-terms`. Confirm whether any other consumer (mobile app, another frontend) needs this GET before treating it as dead code.
- **[low]** `JC/web/admin/js/vendors.js:576-580` — `wizardNext()` in the vendor-create wizard just calls `create()`; it's effectively an unused alias (the "Create" button calls `create()` directly at line 546). Harmless but worth removing to avoid the appearance of a second, different "next step" path.

## PM / UX Suggestions

- **[critical]** Same-invoice re-billing has no guard rail. Because billing is strictly one-receipt-at-a-time ("One bill per receipt" — `stock.js:999`) and `bill_number` has no duplicate check (Technical finding above), a common real-world case — a vendor sends one paper invoice that covers goods received across two or three separate challans/receipts — forces staff to open the bill wizard multiple times and **retype the same bill number, rate, and GST%** each time. Any slip (forgetting it was already billed, or mistyping the bill number differently the second time) either double-pays or silently splits one invoice into untraceable pieces. *Rationale: this is the highest-frequency vendor workflow in the app and currently has zero protection against the most natural mistake a busy staff member will make.*
- **[high]** The "Confirm receive" / "Submit Bill" buttons give no loading/disabled feedback (see Functional finding) — on a slow mobile connection a staff member will very plausibly tap twice, thinking the first tap didn't register. *Rationale: this is a two-line frontend fix that prevents a real money-duplicating bug staff can trigger by themselves.*
- **[high]** Void confirmations are two stacked native browser dialogs — `prompt()` for the reason, then a separate `confirm()` ("Void this receipt? Stock and AP will be reversed...") — for both receipt-void (`stock.js:1993-1995`) and debit-note-void (`debit-notes.js:435-437`). Native dialogs are easy to blow through with muscle-memory Enter/Escape taps, and stacking two of them doubles the chance of an accidental confirm on a financially destructive action (reverses stock + AP). *Rationale: a single custom modal with the reason field and a clear "Void — cannot be casually undone" button is one dialog instead of two and is much harder to fat-finger through.*
- **[medium]** Error wording: `receive_vendor_goods`'s `"no open placed order for this vendor"` (`vendor_receive_bill.py:61`) is developer-speak. A non-technical staff member trying to log goods that arrived without first placing an order in the system has no idea this error means "use Stock-in / offline receive instead." *Rationale: rephrase to something like "This vendor has no pending order to receive against — use 'Stock in' if the goods arrived without an order," turning a dead-end error into a next action.*
- **[medium]** The accountant-only "record payment" flow (`finance.write` role) deliberately hides the vendor's outstanding balance from the person entering the payment amount (`accounts_payable.py:172-187`, by design per its own comment). That's reasonable for hiding *totals*, but it also means the person keying in the payment has nothing on-screen to catch an obvious typo (₹10,000 vs ₹1,00,000) before it posts. *Rationale: at minimum, echo back the entered amount in words (e.g. "₹1,00,000 — One lakh") on the confirmation step so a fat-finger is visually obvious without exposing the running balance.*
- **[medium]** The vendor create wizard's "Opening (₹)" field (`vendors.js:514`) sits right under the primary business-name/phone fields on step 1, while City/GST/Address are tucked behind a collapsed "More" `<details>`. For a brand-new vendor being added mid-conversation with a supplier on the phone, City is arguably more commonly known/needed up front than an opening balance (which is usually 0 for a new vendor). *Rationale: promote City to the main step and fold "Opening balance" into "More" — it's a rarer case (only non-zero for vendors being migrated in with existing dues).*
- **[low]** The "Additional charge" billing-terms field defaults to `100` (`Vendor.additional_charge` server default, `vendor.py:28`) with a generic label "Additional charge" — on the vendor edit screen this reads as an odd default (why would every new vendor start with a flat ₹100 surcharge already configured?). *Rationale: either default to 0 or add an inline hint explaining what this represents (e.g. "printing/packing surcharge some vendors add on top of goods value") so staff don't leave a stray ₹100 charge on vendors who don't actually have one.*
- **[low]** "Billing %" and "GST %" override inputs in the bill wizard (`stock.js:1071-1075`) are plain numeric fields sitting next to the normal bill-total field, with no visual distinction (color/badge) flagging that they're a *one-off deviation from the vendor's usual profile*. Given a wrong entry here silently changes AP math for that bill only, a subtle visual cue (e.g. an "override" chip that appears only when the value differs from the vendor's default) would help staff notice they've strayed from the vendor's normal terms before submitting. *Rationale: reduces the chance of an accidental override sticking around from a previous bill's inputs (the field pre-fills from `receiptMeta`, so a leftover value from billing vendor A's 50%-split invoice could easily carry into vendor B's normal 100% invoice if the wizard state isn't fully reset).*
