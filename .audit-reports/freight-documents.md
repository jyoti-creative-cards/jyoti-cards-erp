# Freight / Dispatch & Document (PDF) Generation Audit — JC ERP

Scope: `JC/backend/app/{models,routers,services}/freight_*`, `app/services/{doc_gen,pdf_documents,customer_bill_pdf,report_pdfs,storage,customer_bill_math,catalog_addons,company_info}.py`, `JC/web/admin/js/{customer-orders,vendor-orders,finance,freight-agents,documents,share}.js`.

Baseline: `cd JC/backend && python3 -m pytest tests/ -q` → **117 passed**. No PDF-rendering tests exist at all (`tests/test_freight_dispatch.py` is the only freight/document-adjacent test file, and it only covers day-scoping).

---

## Technical Findings

- **[high]** `JC/backend/app/services/freight_parcels.py:220-249` — The day-scoping fix is correct for `status=pending` but **incomplete for `status=all`**. The guard is `if day == "today" and status != "pending"`, so when `status="all"` (which is meant to be the pending+picked superset) the day filter still applies. A parcel created yesterday and still unpicked will correctly show under **Dispatch → Pending** with `day=today`, but will **disappear** if the same staff member clicks **Dispatch → All** while still in "Today" hub mode — the exact "silently hides backlog parcels" bug class the fix was supposed to eliminate, just reachable through a different tab. Reproducible today: `goToDispatch()` defaults to `pending` (safe) but `setDispatchStatus('all')` sends `day=today` whenever the hub is in Today mode (`JC/web/admin/js/customer-orders.js:73-75,218-221,306`). Fix: exclude rows with `freight_picked_at IS NULL` from the day filter regardless of the `status` value passed, not just when `status == "pending"`.
- **[high]** `JC/backend/app/routers/vendor_orders.py:1677-1684` and `JC/backend/app/routers/customer_orders.py:1115-1120` — PDF (re)generation failures are swallowed silently (`except Exception: db.rollback()`, no logging, no re-raise). If `generate_vendor_placement_document` / `generate_customer_bill_document` throws (bad image URL, S3 hiccup, malformed totals, etc.), the endpoint just falls through and serves whatever `document_key` already exists — which may be a **stale PDF from before the latest edit**, silently contradicting the code's own comment "Always regenerate so PDF matches current lines (fixes stale empty PDFs)" (`vendor_orders.py:1679`). If there's no existing key at all, it returns a generic `404 "document not available"` that looks identical to "never generated" rather than "generation failed." Compare with the correct pattern already used next door in `JC/backend/app/routers/stock.py:938-947`, which logs and re-raises `HTTPException(500, ...)` with the real error. The two "document" endpoints should match that pattern.
- **[medium]** `JC/backend/app/services/pdf_documents.py:34-47,127,171,305,598` — `_fetch_image()` does one blocking `urllib.request.urlopen(..., timeout=4)` per image, and vendor PO (`_vendor_order_table`), vendor receipt (`_vendor_receipt_table`), customer order receipt (`_items_table`), and customer return (`render_customer_return_pdf`) all fetch images **sequentially, one line at a time**. Only `customer_bill_pdf.py:23-41` (`_prefetch_images_parallel`, 8 workers) parallelizes. A vendor PO/receipt with 20-30 lines and a slow/unreachable image host can take up to 2 minutes and risks a request timeout (Railway/gunicorn worker or browser fetch) — i.e. the single highest-traffic vendor document types have the least resilient image handling. Recommend reusing the same `ThreadPoolExecutor` prefetch helper everywhere images are fetched.
- **[medium]** `JC/backend/app/services/permissions.py:33-58` — `parse_permissions()` auto-expands `vendor_orders.read`/`.write` into `customer_orders.read`/`.write` + `returns.read`/`.write` **unless the staff record already has at least one `customer_orders.*`/`returns.*` permission saved**. This "legacy migration" runs on every permission parse, not just for old rows, so a **brand-new** staff account created today with only "Vendor Orders → View" checked in the UI will, at runtime, also be able to view customer orders/bills — including customer bill PDFs, addresses, phone numbers, and outstanding balances (via `share.py`'s `bill_pdf`, which itself independently accepts either `customer_orders.read` **or** `vendor_orders.read`, see `JC/backend/app/routers/share.py:45`). There is currently no way to create a vendor-only staff role without also granting customer-order visibility. Worth a deliberate fix (e.g. gate the migration on a `legacy=true` flag set at staff creation time, or a one-time DB migration that rewrites old JSON to explicit split permissions, then remove the runtime expansion).
- **[medium]** `JC/backend/app/services/company_info.py:6-9` + `JC/backend/.env.example` — `COMPANY_ADDRESS`/`COMPANY_PHONE`/`COMPANY_GST` have no code-level default and are **not present in `.env.example`**; if unset in Railway, `company_lines()` silently renders with just `"JYOTI CREATIVE CARDS"` and nothing else — no address, no "Indore," no GST line — on every vendor PO/receipt (`_party_blocks` in `pdf_documents.py:64-116`). The explicit business requirement ("our company name (Jyoti Creative Cards, Indore)") has no guarantee in code; it's entirely dependent on an undocumented, optional env var. Recommend a hardcoded fallback address/city or a startup check that warns if `COMPANY_ADDRESS` is empty.
- **[medium]** `JC/backend/app/services/freight_parcels.py:263-282` — N+1 queries: `list_parcels()` calls `db.get(Customer, b.customer_id)` twice per row — once inside `_parcel_dict()` (line 178) and again in the city-lookup loop (line 265) — for up to 300 rows each. Not a correctness bug, but doubles customer lookups unnecessarily on every dispatch queue load; worth consolidating into a single batch query (same pattern already used for `agents`/`cities`).
- **[low]** `JC/backend/app/services/customer_bill_pdf.py:110-117` — `_addon_qty()` checks `addon.get("per_unit") or addon.get("quantity") or 1"`, but the addon schema produced by `catalog_addons.py:_addon_row` (line 12-21) only ever has a `"quantity"` key, never `"per_unit"`. Harmless today (falls through to `quantity`), but dead/misleading code that could hide a real bug if the schema ever changes — the two per-line addon renderers (`pdf_documents.py:_items_table` line 320-326 vs `customer_bill_pdf.py:_addon_qty` line 110-117) use different key-lookup logic for what should be identical addon math between the pre-bill Order Receipt and the final Tax Invoice.
- **[low]** Presigned document links (`document_url` returned by `GET /vendor-orders/placements/{id}/document`, `GET /customer-orders/bills/{id}/document`, `GET /documents?prefix=...`) expire after 3600s (`storage.py:150-163`, default `expires=3600`). Product images embedded *inside* PDFs are fetched-and-rasterized at generation time so they're immune to this, but a cached `document_url` left open in a browser tab/detail panel for over an hour (common — the vendor-order detail view fetches it once and reuses it, `vendor-orders.js:2159-2179`) will 403 with a raw S3 XML error page, not an app error. Low real-world frequency but worth a "link may have expired, click again" fallback instead of a bare `window.open`.

**Verified correct (no bug found), worth noting since they were explicit requirements:**
- `pan_number`/PAN is fully absent from the codebase (`grep -ri "pan"` under `JC/` returns nothing related to a PAN field) — confirmed removed, not just hidden.
- Add-ons never reach vendor documents: `generate_vendor_placement_document`/`generate_vendor_receipt_document` (`doc_gen.py:196-244,247-343`) never populate an `"addons"` key on vendor `pdf_lines`, and addon-product procurement (`app/services/addon_stock.py`, `app/routers/addons.py`) never touches `doc_gen.py`/vendor PDFs at all — clean separation.
- Customer bill/order PDFs never include vendor SKU (`our_product_id` only, `customer_bill_pdf.py:150`, `pdf_documents.py:308-311`) and never include `credit_limit` (explicitly not passed from `doc_gen.py:158-167`, and unused even where accepted as a parameter in `customer_bill_pdf.py:475,522`).
- Outstanding-incl.-this-bill is computed after the bill/AR posting (`doc_gen.py:156-159`) and rendered without the credit limit (`customer_bill_pdf.py:436-443`).
- GST/billing-term is applied per-vendor on receipts (`vendor.gst_included`, `vendor.gst_rate_pct`, `doc_gen.py:333-334`), and all optional fields (vendor phone/address/city/GST, customer phone/address/city, narration, notes) are guarded with `if x:` before being appended — no literal `"None"` strings found anywhere in the renderers.

## Functional / Wiring Findings

- **[high]** See Technical finding above re: `vendor_orders.py:1677-1684` / `customer_orders.py:1115-1120` — silent PDF-regeneration failure. Frontend impact: `VendorOrders.openPlacementDoc()` (`vendor-orders.js:2330-2335`) and `VendorOrders.fetchPlacementPdf()` (`vendor-orders.js:2133-2139`) only show a toast if `document_url` is completely missing; if the backend served a **stale** PDF instead of erroring, the UI has no way to detect or warn about that, and staff could hand a vendor an outdated PO/receipt without knowing.
- **[good]** Customer bill Print/Download (`CustomerOrders.openBillDoc`, `customer-orders.js:2065-2082`) has solid, verified error handling: `DocShare.openPdf()` throws on non-2xx with the parsed `detail` message (`share.js:19-24`), the caller catches it and falls back to the legacy `/customer-orders/bills/{id}/document` + presigned-URL flow, and only surfaces a toast if *both* paths fail. This is the best-wired PDF flow in the app and should be the template for vendor-side buttons.
- **[medium]** `list_parcels()` request/response shape matches the frontend exactly (`freight-agents/parcels` query params `agent_id/status/day` ↔ `customer-orders.js:306-311`), and `pickParcel`/`reassignParcel` correctly invalidate the `/freight-agents` cache (`ctx.invalidateCache?.("/freight-agents")`) so the Finance → Freight dues badge refreshes after a pick — confirmed correct.
- **[medium]** `Finance.shareFreightStatement` / freight payment "Print / PDF" button (`finance.js:2007`) routes to `report_pdfs.render_freight_statement_pdf` / `render_freight_payment_pdf`, both of which use bare `getSampleStyleSheet()` styling with **no `_header()`/company branding at all** (no logo bar, no company name/address/GST — see Technical section and PM/UX section below). This isn't a wiring bug, but it means the "Print / PDF" button for a document that is sometimes handed directly to a freight agent produces something visually inconsistent with every other outgoing document in the app.
- **[low]** `FreightReassignIn.freight_charges` accepts `ge=0` including `0`, and `reassign_parcel()` (`freight_parcels.py:151-174`) happily sets `freight_charges=0` on a bus parcel with no warning — the parcel will later go through `pick_parcel()` (`freight_parcels.py:100-149`) treating `amt <= 0` as "no charge to post," silently skipping the freight ledger entry. If a staff member meant to fill in the amount later and forgot, the parcel gets marked picked with zero freight cost and no ledger trace, which could under-bill the freight agent relationship. No UI warning exists for "reassigning with a 0 amount."
- **[low]** `list_agent_parcels` (`freight_agents.py:223-232`, used by `GET /freight-agents/{id}/parcels`) doesn't expose a `day` filter at all — fine since nothing in the current frontend calls it (dead/unused-by-UI endpoint as far as this audit could find), but worth confirming it's genuinely unused before assuming it's safe from the same day-scoping question.

## PM / UX Suggestions

- **[critical]** *Document consistency.* Vendor PO / vendor receipt / customer order / customer tax invoice PDFs are all professionally branded (blue header bar, company block, styled tables) via `_header()`/`_party_blocks()` in `pdf_documents.py`. Freight agent **statements** and **payment receipts** (`report_pdfs.py:183-281`) — which are handed to freight agents just like vendor documents are handed to vendors — are plain, unbranded, default-ReportLab-style text dumps with no logo, no company address, no GST line. A freight agent receiving this payment receipt would see a document that looks nothing like the rest of the company's paperwork and lacks the basic professionalism (and GST/company identity) a small business needs on anything handed to a third party. Recommend reusing `_header()` + `_party_blocks()` + `_totals_block()` for these two documents.
- **[high]** *Dispatch queue "All" tab is misleading (ties to the Technical finding above).* From a staff perspective, "All" should always be a superset of "Pending" + "Picked." Today it can show *fewer* pending parcels than the "Pending" tab if any of them are older than today and the hub is in "Today" mode. This will look like a data-loss bug to daily staff, exactly the kind of confusion the original day-scoping fix was meant to prevent.
- **[high]** *No page numbering on multi-page documents.* None of the ReportLab builders (`doc.build(story)` calls throughout `pdf_documents.py`, `customer_bill_pdf.py`) register an `onPage`/canvas callback for footers or "Page X of Y." A tax invoice with many line items, or a multi-copy bill (`render_copies_pdf`, `ORIGINAL`/`DUPLICATE`/etc.), can span several pages with **no way to tell if a page is missing** once printed and separated — a real problem for a small business handing paper invoices to customers/vendors. Add a simple page-number footer.
- **[medium]** *Freight dispatch has no "assign agent" bulk action.* Looking at `customer-orders.js:392-420`, agent reassignment is one parcel at a time via a modal. For a company shipping many wedding-card orders through a handful of transporters, batch-assigning a same-day set of pending parcels to one agent (then batch-marking picked) would save meaningful daily staff time versus per-row clicks.
- **[medium]** *No visual distinction for "no image" vs "image failed to load."* `_fetch_image` returning `None` renders an empty table cell in every document type (`pdf_documents.py:127,171,305,598`). Staff can't tell whether a product genuinely has no photo on file or the fetch silently failed (network blip, expired URL, deleted S3 object). A small "no image" placeholder icon (rendered locally, not fetched) would remove the ambiguity without needing a network round-trip.
- **[medium]** *Freight ledger detail has no day/date-range filter or search*, unlike almost every other list in the admin (Documents, Freight agents setup, Finance AR/AP all have search bars). For an agent with a long relationship and hundreds of entries, finding "that one bill from March" means scrolling the full reversed ledger.
- **[low]** *"Change agent" reassignment modal defaults the amount field to blank* ("Leave blank to keep") rather than pre-filling the parcel's current freight charge — small friction, since staff can't see what they're changing from without checking the row first.
- **[low]** *Freight statement/payment PDFs show raw negative formatting via Python's `,.2f`* (`report_pdfs.py:26`) rather than the Indian-digit-grouping + explicit sign helper used everywhere else (`customer_bill_pdf.py:_money`), so numbers there look formatted differently (`Rs.1,234.56` international grouping vs `Rs. 1,234.56` Indian grouping used on bills) — small but noticeable polish gap between document types, reinforcing the "these look like a different app" impression from the critical finding above.
